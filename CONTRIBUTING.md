# Contributing

Thanks for looking. This is a small project with a deliberately narrow job, so the most useful
thing to read first is what it is not trying to be.

## The scope, so you do not waste your time

This is **a remote**. It sends key presses to an Android TV and shows what the TV reports back.

Out of scope, and likely to be declined however well built:

- **Managing the TV** — installing or removing apps, changing settings, file transfer. The app
  uses ADB as a transport for devices that have no remote service, but it is still a remote;
  [cleanyourtv](https://github.com/amrakshay/cleanyourtv) does the debloating half of it.
- **A cloud component, an account, or anything that needs the internet.** The app talks to one
  device on your Wi-Fi and nothing else, and that is worth keeping.
- **Media playback in the app.** It drives the TV; the TV plays things.

In scope and welcome: voice (the protocol supports streaming the microphone and this does not use
it), better app shortcuts, reconnection behaviour, accessibility, and support for TVs other than
the one it was built against.

## Getting set up

No Android Studio required — the Gradle wrapper is checked in.

```bash
# JDK 17 or newer, and the Android SDK:
sdkmanager "platform-tools" "platforms;android-37.2" "build-tools;37.0.0"
echo "sdk.dir=$ANDROID_SDK_ROOT" > local.properties

./gradlew :protocol:test        # no device, no emulator, a few seconds
./gradlew :app:assembleDebug
```

### The protocol module has no Android dependency, on purpose

Everything the protocol needs — TLS, crypto, protobuf, coroutines — is standard Java, so
`protocol/` is a plain JVM module. That is what lets the whole protocol be tested on a desktop and
driven against a real TV with no phone in the loop:

```bash
./gradlew :protocol:tvcli --args="pair   192.168.0.236 creds"
./gradlew :protocol:tvcli --args="keys   192.168.0.236 creds VOLUME_DOWN HOME"
./gradlew :protocol:tvcli --args="search 192.168.0.236 creds the bear season 3"

./gradlew :protocol:tvcli --args="adb-info 192.168.0.138 creds"
./gradlew :protocol:tvcli --args="adb-keys 192.168.0.138 creds DPAD_DOWN DPAD_UP"
```

**Please keep it that way.** The moment it imports `android.*`, the tests need a device and the
CLI stops working, and both of those paid for themselves repeatedly while this was being built.

### Two transports behind one interface

`Remote` is the seam: `RemoteSession` speaks the TV's own protocol, `AdbRemote` drives adbd for
devices that have no remote service. Anything the two cannot both do belongs in `Capabilities`
rather than in a branch in the UI — the point is that the screen can say what a device actually
does instead of offering a control that silently fails.

The ADB side is `shell:` streams and monkey's command port, nothing exotic, but two measurements
shaped it and are worth not rediscovering: `input keyevent` costs about 300 ms a press on this
class of hardware, and a persistent interactive shell does not help, because the cost is `cmd`
starting up rather than the stream. monkey answers in about 70 ms. Keys go through monkey;
everything else is a one-shot `shell:` stream, which ends cleanly when the device closes it.

### The Python implementation is the oracle

The pairing hash is pinned to vectors generated by
[`python-androidtvremote2`](https://pypi.org/project/androidtvremote2/), the library Home Assistant
uses. If you change anything in `Certs.kt`, check the result against that library rather than
against a TV — the TV only ever answers "no", with no indication of why.

`spike/` is a Dart implementation of the same protocol, kept as a second reference for the same
reason. It is not built or shipped.

The ADB public key encoding has an oracle of its own: `adb keygen` writes the same structure, so
`AdbKeyTest` pins the Kotlin encoder to a key that `adb` itself generated. Change `AdbKey.kt` and
check it against a fresh `adb keygen` rather than against a device — adbd's answer to a malformed
key is to go quiet.

### The generated protobuf is committed

`protocol/src/main/java/` is `protoc` output and is checked in, so a clone needs no protobuf
toolchain. To regenerate it from `spike/proto/atv.pb`:

```bash
protoc --descriptor_set_in=spike/proto/atv.pb --java_out=lite:protocol/src/main/java \
  polo.proto remotemessage.proto
```

The `protobuf` version in `gradle/libs.versions.toml` must match the `protoc` that generated it.

## House style

- Comments explain **why**, especially where the code looks wrong but is not. Several things here
  are deliberate and surprising: `BigInteger.toByteArray()` cannot be used for the pairing hash
  or the ADB public key, writes must not happen on the caller's thread, `START_LONG`/`END_LONG`
  are not a substitute for `SHORT`, and an interactive ADB shell echoes everything you send it
  back at you. Each of those has a comment saying so, because each was a bug first.
- British spelling in prose, American in code identifiers where the platform uses it.
- No new dependency without a reason that a paragraph can justify.

## Tests

```bash
./gradlew :protocol:test
```

New protocol behaviour wants a test. Framing and the pairing hash are the two places where a
subtle mistake produces a silent failure rather than an error, so they have the most.

### Test on a real device

This matters more than usual here. Every bug found so far was about **where code runs or how fast
events arrive** — a main-thread socket write, a gesture that fires two messages too close
together, a sheet that did not close — and the test suite could not have caught any of them.

`docs/PLAN.md` has a section listing what has been exercised on hardware and what has not. If you
change something in that list, please update it.

## Pull requests

- Say what is different for someone using the app, not only what changed in the code.
- Say what you tested it on. "Built and ran on a Pixel 6 (Android 14) against a Sony Bravia" is
  worth more than a green CI run.
- Update `docs/PLAN.md` and `CHANGELOG.md` if behaviour changed.

## Versioning

The version lives in [`VERSION`](VERSION) and the Android build reads it, deriving `versionCode`
from it (`1.2.3` becomes `10203`). A release is one edit, not two that can disagree.

## Releasing

Push a `v*` tag and the release workflow does the rest: it checks the tag against `VERSION`,
builds, signs, verifies the signature with `apksigner`, pulls the notes out of `CHANGELOG.md`
and publishes the APK. CI signs from repository secrets.

To sign locally:

```bash
source tools/release-env.sh && ./gradlew :app:assembleRelease
```

**There is no keystore and no password anywhere in this repository, and there must not be.** It
is public, and a signing key committed here would let anyone build an APK that Android accepts
as an upgrade to this one — a key that has been published cannot be withdrawn. The password and
the keystore live in the macOS login Keychain, under the account `atvremote`:

| Service | Holds |
|---|---|
| `android-tv-remote-keystore-password` | the store and key password |
| `android-tv-remote-keystore-base64` | the keystore itself |

`tools/release-env.sh` reads both and rebuilds `~/.android-tv-remote/release.keystore` when it
is missing, so the file on disk is a cache and the Keychain is the source. With iCloud Keychain
on, that is also the off-machine backup.

**If both the Keychain entries and the GitHub secrets are lost, the key is gone**, and no future
release can upgrade an installed copy in place — people would have to uninstall, losing their
pairing.
