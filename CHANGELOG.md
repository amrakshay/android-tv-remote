# Changelog

All notable changes are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses
[semantic versioning](https://semver.org/).

The version lives in one place, the [`VERSION`](VERSION) file, which the Android build reads at
configure time — so the APK and the repository cannot ship disagreeing numbers.

## [Unreleased]

### Added

- **Devices with no TV Remote Service are now supported, over ADB** ([#1](https://github.com/amrakshay/android-tv-remote/issues/1)).
  A good many TV boxes and projectors run a full Android TV image without
  `com.google.android.tv.remote.service`, so nothing listens on 6466 and no phone remote can
  reach them. They do run adbd. The app now speaks both and picks by what the device advertises.
  - `protocol/adb/` — an ADB client in plain Kotlin: the wire format, the `AUTH` exchange
    (signature, then the public key, which is what raises the device's "Allow debugging?"
    prompt), and stream multiplexing. No new dependency.
  - Keys and text go through monkey's command port, about 70 ms a press. `input keyevent` was
    measured at about 300 ms on this hardware, which is unusable as a remote.
  - Everything else — volume, the foreground app, the app list — is a one-shot `shell:` stream,
    where the cost does not matter and the output has a clean end.
  - **The app list is read off the device**, so every tile really is installed. Launchers are
    left out, and names come from a short table of the common packages, falling back to a
    tidied-up package name.
  - **Typing reaches apps that draw their own keyboard**, YouTube included, which the remote
    protocol cannot do. It types at the cursor rather than replacing the field, so the keyboard
    sheet offers a backspace in place of a clear.
  - Discovery browses `_adb._tcp` as well as `_androidtvremote2._tcp`, ignores this phone's own
    advertisement, and lists a device that answers to both only once, as a TV.
  - A typed-in address probes 6466 and then 5555, so nobody has to know which transport they are
    on.
- A `Remote` interface with a `Capabilities` record behind both transports, so the UI states what
  a device can actually do instead of offering a control that quietly does nothing.
- `tvcli` gained `adb-info`, `adb-keys`, `adb-text` and `adb-launch`, so the second transport is
  as drivable from a desktop as the first.

### Verified on hardware

- From the OnePlus 7 against the projector: discovery, the typed-address probe, volume, D-pad,
  app launch, the real app list, and "the bear" typed into YouTube's search with results.
- The native path re-checked on the same build, since both transports now sit behind one
  interface: paired with the Xiaomi, volume 59 → 56 → 59 pushed back live by the TV.
- `AUTH` reaches a real device — run against the Xiaomi it raised the TV's own "Allow debugging?"
  dialog — but was not carried through to a grant, so the post-acceptance leg is covered only by
  the `adb keygen` vector.

### Tests

- 11 more, 31 in all. The ADB public key encoding is pinned to a key generated by `adb keygen`
  itself — the same oracle discipline as the pairing hash, and for the same reason: a wrong byte
  there is not an error, it is a device that silently never authorises.

## [1.0.0] — 2026-10-30

First release. A phone remote for an Android TV that installs nothing on the TV: pair once with
a code shown on screen, and it works from then on. Verified end to end against a Xiaomi
MiTV-AXSO0 from a OnePlus 7.

### Added

- **`protocol/`** — the Android TV remote protocol v2 in plain Kotlin, with no Android dependency,
  so all of it unit-tests on a desktop.
  - Length-delimited protobuf framing that survives a split anywhere, including inside the length
    varint itself.
  - Client certificate generation — RSA-2048, `CN=atvremote` — matching the reference
    implementation down to the `basicConstraints` extension.
  - The pairing handshake on port 6467, with the SHA-256 secret and the checksum that catches a
    mistyped code locally, before the TV is asked.
  - The session on port 6466: key injection, press-and-hold, text entry, app launch by deep link,
    and the ping keepalive the TV hangs up without.
  - What the TV pushes back — volume, power, the running app, the focused text field — as
    `StateFlow`s.
  - `tvcli`, a desktop harness that drives a real TV with no phone involved.
- **`app/`** — the phone app, in Compose.
  - Discovery with `NsdManager`, holding a multicast lock and serialising resolves, plus a typed
    address for networks that block mDNS.
  - A hex keypad for pairing, because the code is `0-9 A-F` and a numeric keypad would be wrong.
  - The remote: D-pad, volume with the TV's live level, media transport, app shortcuts and a
    keyboard sheet.
  - An honest unreachable state, since this TV cannot be woken over the network.
- **`spike/`** — a Dart implementation of the same protocol, kept as a second reference.
- **Tests** — 12, covering framing against adversarial splits and the pairing hash pinned to
  vectors generated by `python-androidtvremote2`.

### Fixed

Three bugs that only running the app could find, all invisible to the tests:

- **Every key press was silently dropped.** Writes went out on the caller's thread, which on
  Android is the main thread, so `NetworkOnMainThreadException` was thrown and swallowed by a bare
  `runCatching`. The app looked alive the whole time, because the reader has its own thread — so
  volume and current-app updates kept arriving while nothing we sent ever left. Writes now go
  through a `limitedParallelism(1)` IO dispatcher, which also keeps them ordered, and failures are
  logged.
- **Hold-to-repeat broke plain taps.** Sending `START_LONG` immediately followed by `END_LONG`
  looks like a press, but the TV ignores the pair when they arrive back to back. A tap now sends
  `SHORT`; only a press held past 350 ms switches to the long pair.
- **The Apps sheet stayed open after launching an app**, hiding the remote and swallowing the next
  tap.

### Known limitations

- The TV cannot be switched on. It leaves the network entirely in standby and does not wake on
  LAN — see [docs/PLAN.md](docs/PLAN.md) §4.4 for the measurements.
- Typing reaches apps that use a standard Android text field. Apps that draw their own keyboard
  into a `SurfaceView`, YouTube among them, report no field and cannot be typed into.
- App shortcut deep links are best guesses apart from YouTube, which is verified.
- Window insets are not handled, so the header sits close to the status bar.
- iPhone is not supported.
