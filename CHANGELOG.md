## [1.0.0] — 2026-10-30

First release. A phone remote for an Android TV that installs nothing on the TV: pair once with
a code shown on screen, and it works from then on. Verified end to end against a Xiaomi
MiTV-AXSO0 from a OnePlus 7.

### Added

- **`protocol/`** — the Android TV remote protocol v2 in plain Kotlin, with no Android dependency,
  so all of it unit-tests on a desktop.
  - Length-delimited protobuf framing that survives a split anywhere, including inside the length
    varint itself.
  - Client certificate generation — RSA-2048, `CN=atvremote` — matching the reference
    implementation down to the `basicConstraints` extension.
  - The pairing handshake on port 6467, with the SHA-256 secret and the checksum that catches a
    mistyped code locally, before the TV is asked.
  - The session on port 6466: key injection, press-and-hold, text entry, app launch by deep link,
    and the ping keepalive the TV hangs up without.
  - What the TV pushes back — volume, power, the running app, the focused text field — as
    `StateFlow`s.
  - `tvcli`, a desktop harness that drives a real TV with no phone involved.
- **`app/`** — the phone app, in Compose.
  - Discovery with `NsdManager`, holding a multicast lock and serialising resolves, plus a typed
    address for networks that block mDNS.
  - A hex keypad for pairing, because the code is `0-9 A-F` and a numeric keypad would be wrong.
  - The remote: D-pad, volume with the TV's live level, media transport, app shortcuts and a
    keyboard sheet.
  - An honest unreachable state, since this TV cannot be woken over the network.
- **`spike/`** — a Dart implementation of the same protocol, kept as a second reference.
- **Tests** — 12, covering framing against adversarial splits and the pairing hash pinned to
  vectors generated by `python-androidtvremote2`.

### Fixed

Three bugs that only running the app could find, all invisible to the tests:

- **Every key press was silently dropped.** Writes went out on the caller's thread, which on
  Android is the main thread, so `NetworkOnMainThreadException` was thrown and swallowed by a bare
  `runCatching`. The app looked alive the whole time, because the reader has its own thread — so
  volume and current-app updates kept arriving while nothing we sent ever left. Writes now go
  through a `limitedParallelism(1)` IO dispatcher, which also keeps them ordered, and failures are
  logged.
- **Hold-to-repeat broke plain taps.** Sending `START_LONG` immediately followed by `END_LONG`
  looks like a press, but the TV ignores the pair when they arrive back to back. A tap now sends
  `SHORT`; only a press held past 350 ms switches to the long pair.
- **The Apps sheet stayed open after launching an app**, hiding the remote and swallowing the next
  tap.

### Known limitations

- The TV cannot be switched on. It leaves the network entirely in standby and does not wake on
  LAN — see [docs/PLAN.md](docs/PLAN.md) §4.4 for the measurements.
- Typing reaches apps that use a standard Android text field. Apps that draw their own keyboard
  into a `SurfaceView`, YouTube among them, report no field and cannot be typed into.
- App shortcut deep links are best guesses apart from YouTube, which is verified.
- Window insets are not handled, so the header sits close to the status bar.
- iPhone is not supported.
